## 一、项目定位与文档目的

### 1.1 软件定位

本项目针对现有 AI 情感陪伴产品的四大缺陷——**单维文本感知、被动响应模式、碎片化记忆、高表达门槛**，构建「实时生理感知 → 情绪识别 → 主动干预 → 长期陪伴」完整闭环。

本目录实现闭环中除硬件固件与 Flutter APP 之外的**全部软件部分**：

| 层次 | 本目录实现 | 外部配套 |
|------|-----------|---------|
| 硬件感知层 | 传感器模拟器 `core/simulator.py` + 桥接层 `esp32_firmware/bridge.py` | ESP32 四模态终端固件（陈泽鲲负责） |
| 分析处理层 | `algorithms/` HRV 提取 · 信号质量门禁 · 三层情绪识别 · PAD 回归 · 情感动力学 · 主动触发决策 | — |
| AI 生成输出层 | `agent/` 陪伴 Agent「小暖」+ FTA 记忆 + 情绪策略 + TTS + **九大工具** | LLM API（DeepSeek 等 OpenAI 兼容服务） |
| 应用层 | `backend/` FastAPI 服务（20+ 端点 + WebSocket） | Flutter APP（陈彦冰负责） |

### 1.2 文档目的与"极致的专业"的定义

本文档是本目录的**唯一完整技术说明**，用于支撑：项目结题材料、答辩技术问答、后续同学接手、以及论文方法学章节的撰写。

本项目对"专业"的落地定义是四条**同时**满足：

1. **有文献依据** —— 每个方法都能指到具体文献的具体公式或结论（见 §11 映射表）；
2. **有可运行代码** —— 不是"计划实现"，而是当前仓库里就能跑；
3. **有断言其行为的测试** —— 不是"看起来对"，而是有一条测试会因为改坏它而失败；
4. **有明示的边界** —— 写清什么情况下不成立、不可用于哪类结论。

凡不满足全部四条者，本文档一律标记为 ⚠️ 或 ❌，**而不是让它看起来能用**。

## 二、系统总体架构

### 2.1 数据链路总览（四模态）

```
┌───────────────────────── ESP32 可穿戴终端（四模态）──────────────────────────┐
│                                                                             │
│  MAX30102 (0x57)      PPG 光电容积脉搏波      → 逐拍 IBI / 心率              │
│  MPU6050  (0x68)      六轴惯性                → 运动伪迹门控（三判据取或）    │
│  ADS1115  (0x48)      16bit ADC               → GSR 皮电（A0，唯一非总线线） │
│  呼吸带（预留）        胸腹呼吸                 → 直接呼吸率 / RSA 交叉校验    │
│                                                                             │
│  三条供电铁律：① GSR 与 ADS1115 同 3.3V；② MAX30102 模块亦 3.3V；③ 全部共地  │
│  I2C 并联：SDA=GPIO21 / SCL=GPIO22 / 上拉并联 ≈3.3kΩ / 400kHz               │
│  采样与门控 → 运动期只跑滤波器、不记峰 → 1 包/秒 契约包（9 字段）            │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   │ BLE 5.0 / USB 串口
                                   ▼
┌──────────────────────── hrv_companion_agent ────────────────────────────────┐
│                                                                             │
│  【契约层】 core/system.py :: ingest_sensor(packet)                         │
│                     │                                                       │
│  【算法层】 algorithms/                                                     │
│   ① HRVExtractor      时域 + Welch 频域 + 非线性 + 伪迹清洗                 │
│   ② quality_metrics   ★ jitter = RMSSD/mean(IBI) 信号质量门禁               │
│   ③ EmotionRecognizer 三层识别（规则 → 模糊 → ML）→ 5 类情绪 + 风险分       │
│   ④ PADRegressor/     ★ 19 维 → PAD 连续三维（RulePAD 兜底）                │
│     RulePAD                                                                 │
│   ⑤ EmotionDynamics   ★ 文献3 式(11)–(20) 情绪强度/时长/衰减/心境           │
│   ⑥ TriggerEngine     ★ 风险合成 + 质量门禁 + 连续确认 + 冷却 + 自适应阈值   │
│                     │                                                       │
│  【Agent 层】 agent/                                                       │
│   ⑦ 记忆管理器        ★ FTA 五元组 + 混合检索 + 时序链接 + 遗忘曲线         │
│   ⑧ 九大工具          ★ 感知 / 干预 / 校准 / 记忆 / 安全 分层               │
│   ⑨ 小暖 Agent        提示词注入 + 情绪转场 + 主动关怀 + 工具循环           │
│   ⑩ TTS               Edge-TTS（可选，超时降级）                           │
│                     │                                                       │
│  【应用层】 backend/routes.py  → 20+ REST 端点 + WebSocket 流式对话         │
│             backend/views.py   → 状态视图换算（纯函数，可单测）             │
│                                                                             │
│  持久化：data/memory.db（SQLite）  可选：ChromaDB 向量后端                  │
└──────────────────────────────────┬──────────────────────────────────────────┘
                                   │ HTTP / WebSocket
                                   ▼
                      Flutter APP（数据可视化 / 聊天 / 历史回顾）
```

### 2.2 分层职责一览

| 层 | 目录 | 职责 | 不该做的事 |
|----|------|------|-----------|
| 契约层 | `core/system.py` | 收包、解析、调度、缓存 | 不做算法（一律调用 algorithms） |
| 算法层 | `algorithms/` | 纯计算，输入数字输出数字 | 不碰数据库、不碰 LLM、不打印 |
| Agent 层 | `agent/` | 判断用户处境、选技能、组织语言 | 不做生理计算、不直接读串口 |
| 应用层 | `backend/` | 协议转换、鉴权、多用户隔离 | 不写业务判断（复用 core） |

> **设计纪律**：`backend/views.py` 被刻意抽成**不依赖 FastAPI 的纯函数**。
> 原因很实际：本机开发环境不保证装了 Web 框架，而"PAD 值怎么换算成紧张程度"
> 这类逻辑恰恰是最容易出错、最需要单测的部分。抽出来之后，这部分
> **没有 FastAPI 也能被 26 条测试覆盖**。

## 四、环境安装与配置

### 4.1 环境要求

- Python ≥ 3.9（开发环境为 3.13）
- **离线演示模式仅需** `python-dotenv` —— 其余依赖缺失时全部自动降级，闭环依然完整可跑

### 4.2 安装

```bash
cd hrv_companion_agent
pip install -r requirements.txt            # 核心
pip install -r requirements-optional.txt   # 可选：ML / TTS / API / 向量库
```

各依赖缺失时的自动降级行为：

| 依赖 | 缺失时行为 |
|------|-----------|
| hello-agents | 使用内置兼容实现（外部接口保持一致） |
| openai / `LLM_API_KEY` | 离线规则话术库（演示模式，零费用） |
| scikit-learn / joblib | Layer 3 跳过、PAD-SVR 跳过（规则 + 模糊 + RulePAD 仍可用） |
| numpy | 频域改用纯 Python Lomb-Scargle 粗网格实现（精度下降，见 §6.1.2） |
| fastapi / uvicorn | 仅无法启动 API，其他功能正常（`backend/views.py` 仍可单测） |
| edge-tts | TTS 静默跳过（纯文本交互） |
| chromadb | 语义检索降级为字符 bigram 重叠系数（**边界见 §7.3.5**） |

> **一句话结论**：本系统**没有硬依赖**，任意依赖缺失都不会让核心闭环崩掉。
> 这是刻意的设计选择 —— 答辩现场的网络与机器不可控。

### 4.3 环境变量（`.env`）

复制 `.env.example` 为 `.env` 后修改。**程序启动时自动加载**项目目录或上级目录中的 `.env`（无需手动 export），Key 变量名兼容多种写法（`LLM_API_KEY` / `DEEPSEEK_API_KEY` / `OPENAI_API_KEY` / `DASHSCOPE_API_KEY` 等任选其一）。

| 变量 | 默认 | 说明 |
|------|------|------|
| `LLM_MODEL_ID` | 按 Key 推断 | 模型名须与服务商一致 |
| `LLM_API_KEY` | 空 | **留空 = 离线演示模式** |
| `LLM_BASE_URL` | `https://api.deepseek.com` | OpenAI 兼容地址（通义/Kimi/Ollama 均可） |
| `LLM_TEMPERATURE` | 0.7 | 基础回复温度（受情感动力学调制，见 §6.5） |
| `LLM_MAX_TOKENS` | 1024 | 单次生成上限 |
| `LLM_TIMEOUT` | 60 | 秒 |
| `TTS_ENABLED` | 0 | 1 = 启用 Edge-TTS（合成超时 8 秒，失败不影响文字回复） |
| `TTS_VOICE` | `zh-CN-XiaoyiNeural` | 温暖女声 |
| `ML_MODEL_PATH` | `models/emotion_model_rf.joblib` | Layer 3 模型路径 |
| `CHROMA_ENABLED` | 0 | 1 = 启用 ChromaDB 真向量检索 |

常见模型名（以服务商实际支持为准）：
- DeepSeek：`deepseek-v4-flash` / `deepseek-v4-pro` / `deepseek-chat`
- 通义千问：`qwen-plus` / `qwen-turbo`；Kimi：`moonshot-v1-8k`
- 本地 Ollama：`http://localhost:11434/v1` + `qwen2.5:7b` 等

**模型名填错时系统会自动纠错**（解析错误信息中的可用模型名并切换），且启动时执行一次 1-token 真实对话探测（健康检查），把 Key / 模型 / 网络问题在第一条消息之前就暴露出来。

### 4.4 常用能力开关

v2 新增的模块**全部可独立开关**，便于做消融实验（论文里"去掉 X 模块后指标变化"这一节可以直接靠环境变量跑出来）：

| 变量 | 默认 | 作用 | 关闭后的影响 |
|------|------|------|-------------|
| `QUALITY_GATE_ENABLED` | 1 | 信号质量不合格 → 降置信度 + 抑制触发 | 低质量数据也会被当真（**不建议关**） |
| `PAD_ENABLED` | 1 | PAD 三维估计 | 不注入维度倾向，情绪只有离散标签 |
| `DYNAMICS_ENABLED` | 1 | 情感动力学状态机 | "有点焦虑"与"极度焦虑"将无法区分 |
| `MEMORY_FTA_ENABLED` | 1 | FTA 情境记忆（五元组） | 退化为 v1 的互动流水记忆 |
| `SELF_REPORT_ENABLED` | 1 | 主观自评通道（**实验真值来源**） | 无法验证 >85% 指标（**实验期不要关**） |
| `TRIGGER_MIN_CONSECUTIVE` | 1 | 需连续 N 次越阈值才触发 | 设为 3 可显著降低单点误报 |
| `EXPOSE_RAW_METRICS` | 0 | 调试用：把原始生理值暴露给 Prompt 与 API | — |
| `MEMORY_FORGET_ENABLED` | 1 | 遗忘曲线 + 归档 | 记忆无限累积，检索信噪比下降 |
| `LLM_PARAM_MODULATION` | 1 | 用情感状态调制 temperature / top_p | 所有情绪下回复风格趋同 |
| `SAFETY_ENABLED` | 1 | 安全层（危机分级 / 转介） | **绝不可关，仅用于对比实验** |

> ⚠️ `EXPOSE_RAW_METRICS=1` 会关闭"只给语义区间"的保护。**仅用于调试与论文绘图**。
> 正式演示请保持 0 —— 否则模型可能在回复里复述"你的心率是 96 bpm"，
> 破坏产品设定（也是同类产品被用户诟病最多的一点）。

### 4.5 配置纪律：语义区间集中定义

v1 存在一个隐蔽问题：**风险等级与质量等级的文案在两处各写了一份**
（视图层 `backend/` 与提示词层 `agent/prompts.py`）。两份不一致时不会报错，

## 六、算法层详解

### 6.1 HRV 特征提取（`algorithms/hrv_extractor.py`）

**输入**：IBI 序列（心跳间隔 ms）或 BLE 契约包；**输出**：特征字典（时域 + 频域 + 非线性）。

#### 6.1.1 时域特征 ✅

| 特征键 | 含义 | 生理意义 |
|--------|------|---------|
| `hr_bpm` | 心率 | 唤醒度粗指标 |
| `mean_ibi_ms` | 平均 NN 间期 | — |
| `sdnn_ms` | NN 间期标准差 | 总自主神经活性 |
| `rmssd_ms` | 相邻 NN 差值均方根 | **副交感活性**（短时） |
| `sdsd_ms` | 相邻差值标准差 | RMSSD 的伴随量 |
| `pnn50_pct` | \|ΔNN\| > 50ms 占比 | 短时迷走调节 |
| `sd_hr_bpm` | 心率标准差 | 供 ML 层使用 |
| `sdnn_index_ms` | 5 分钟窗平均 SDNN | 长时稳定性 |

#### 6.1.2 频域特征 ✅（v2 重写）

**v2 变更**：v1 使用 Lomb-Scargle 周期图（纯 Python 粗网格），存在**频率轴失真**（约 0.85×，
即算出的 LF/HF 中心频率整体偏移）。v2 改为：

```
去趋势 → 4 Hz 线性插值重采样（把不等间隔 RR 变成等间隔序列，
         并保证 Nyquist=2Hz 足以覆盖 HF 上限 0.4Hz）
       → Welch 平均周期图（分段 + 汉宁窗 + 段间重叠 → 平均）
       → 频带积分
```

| 频带 | 范围 | 主要成分 |
|------|------|---------|
| VLF | 0.003–0.04 Hz | 体温调节、慢速调节（短窗不可靠） |
| LF | 0.04–0.15 Hz | 压力感受器 + 交感/副交感混合 |
| HF | 0.15–0.40 Hz | **呼吸性窦性心律不齐 RSA → 副交感** |

派生量：`total_power_ms2`、`lf_hf`（交感-副交感平衡）、`lf_nu` / `hf_nu`（归一化单位）。

> ⚠️ **注意事项**：频域指标在 **< 2 分钟**窗口下噪声很大；本项目 `HRV_WINDOW_SEC=300`，
> 但演示场景常只有几十秒。**不要用几十秒的数据去论证 LF/HF**。
> 📌 论文中报告频域指标时必须写明窗口长度。

#### 6.1.3 非线性特征 ✅（v2 新增）

| 特征键 | 方法 | 意义 |
|--------|------|------|
| `sd1_ms` / `sd2_ms` | **真椭圆拟合**（45° 旋转法） | Poincaré 图短轴/长轴：SD1 ≈ 短时变异，SD2 ≈ 长时变异 |
| `sampen` | 样本熵 SampEn(m=2, r=0.2×SD, Chebyshev 距离) | 序列复杂度，低值 = 规律/僵硬（常见于高应激） |
| `dfa_alpha1` | 去趋势波动分析，尺度 4–16 拍 | 短程分形相关 |
| `dfa_alpha2` | 去趋势波动分析，尺度 16–64 拍 | 长程分形相关 |

**v2 修正**：v1 的 SD1/SD2 用近似式（`SD1² = ½·SDSD²`），在非平稳段有系统偏差。
v2 改为真椭圆拟合 —— 把 Poincaré 散点按 45° 旋转后求两个方向的标准差。

> ⚠️ **样本熵与 DFA 的有效长度要求**：SampEn 一般建议 ≥ 300 拍，DFA α2 建议 ≥ 500 拍。
> 本项目演示窗口常不足此长度，此时这两个值**仅供参考**，不应作为主要判据。

#### 6.1.4 伪迹清洗 ✅

```python
clean_ibi_report(ibi_list) → {
  "cleaned": [...],      # 清洗后序列
  "n_in": N,             # 输入拍数
  "n_out": M,            # 剔除拍数
  "rejected": K,         # 剔除次数
  "ectopic_ratio": ...,  # 伪迹比例
}
```

判据：IBI 超出 `[300, 2000] ms` 或与前拍跳变过大者剔除，并按标准 HRV 关系式迭代离群剔除。

> ⚠️ **实测教训（写入代码注释）**：构造测试用的等幅交替 RR 序列时，
> 交替幅度 **超过约 ±70ms 就会被 `clean_ibi` 当作离群整段剔除**，
> 于是测试看到的是"有效拍数不足"而不是"抖动过大"。
> 这不只是测试构造问题 —— 它说明**清洗阈值与质量门禁存在耦合**：
> 极端抖动会被清洗掉，所以在清洗后序列上算出的 jitter 会**偏低**。
> 质量门禁因此另外记录 `ectopic_ratio` 作为第二判据（见 §6.2）。

**BLE 兼容**：`extract_from_ble()` 优先采用固件已算值，缺失字段由 IBI 重算，
完全缺失时按心率经验式兜底。特征键名与 `mad_toolkit/mad_hrv_extractor.py` 对齐，可互换。

**内存红线** ⚠️：不可缓存长波形。60s × 100Hz = 6000 点会触发 `MemoryError`
（ESP32 侧已实测）。本层只保留 200 点波形 + 512 拍 RR 环。

### 6.2 信号质量门禁（v2 核心新增）✅

#### 6.2.1 为什么需要它

这是本项目**最重要的一条工程教训**，值得单独成节：

> 2026-09-30 实测：手指贴放 MAX30102 时，**HR 显示 73 bpm（看着完全正常），
> 但 RMSSD 高达 130ms、pNN50 61~75%**（静息应为 20~50ms / <10%）。
> 也就是说：**HR 是可信的，HRV 是假的。**

原因在于二者的可信度**天然解耦**：

| 指标 | 计算对象 | 对逐拍抖动（接触不良 / 灌注不足）的敏感度 |
|------|---------|----------------------------------------|
| HR | 峰间距的**均值** | 抖动被**平均掉** → HR 看起来正常 |
| HRV | 相邻峰的**差分** | 抖动**全额进入** → RMSSD 被放大数倍 |

所以"HR 正常"**完全不能**用来推断"HRV 可信"。
下游若不做门禁，就会基于一个虚假的 RMSSD 得出"副交感活性很高/很低"的结论 ——
**不报错，只是静默地算错**。

#### 6.2.2 判据：RR 抖动指数 jitter

```
jitter = RMSSD / mean(IBI)
```

这是唯一能在"HR 完全正常的假象下"把问题揪出来的指标。

| 等级 | 判据（默认） | 含义 | 下游行为 |
|------|-------------|------|---------|
| **合格** | `jitter ≤ 0.08` 且 `ectopic ≤ 0.10` | 生理判断可用 | 正常触发 |
| **勉强** | `jitter ≤ 0.12` 且 `ectopic ≤ 0.20` | 可作参考 | 降置信度，结论以用户自述为准 |
| **不可用** | 超出上述 | 不可用于判断 | **抑制触发** + Prompt 明确告知模型"以用户自述为准" |
| **不足** | 有效拍数 < 5 | 数据积累中 | 不判断 |

实测参考值（指腹贴放，本项目 2026-09-30）：静息合格段 jitter ≈ 0.02~0.06；
接触不良时达 **0.455**。

阈值全部取自 `config`（`QUALITY_JITTER_GOOD` / `QUALITY_JITTER_POOR` /
`QUALITY_ECTOPIC_GOOD` / `QUALITY_ECTOPIC_MAX`），并由测试验证"改配置会改变判定结论"
（`test_relaxing_threshold_changes_verdict`）—— 证明配置不是装饰。

#### 6.2.3 可下手的 `reason` 字段 ✅

只说"不可用"会让使用者无从下手，v2 因此要求区分**首要原因**并给出可操作建议：

```python
elif ectopic > ect_max and jitter <= j_poor:
    reason = f"伪迹比例过高（{ectopic:.0%} > {ect_max:.0%}），请检查电极/指腹接触是否稳定"
elif jitter > j_poor:
    reason = f"逐拍抖动过大（{jitter:.3f} > {j_poor}），多为接触不良或灌注不足，HR 可能仍显示正常"
```

两类原因的**改善措施完全不同**：前者是异位搏动/漏检/双计（算法侧），
后者是接触与灌注问题（佩戴侧）。混在一起报"不可用"等于没报。

> 📌 **论文怎么写**：这一节可以直接作为"为什么单模态 PPG 的情绪识别存在系统性高估"
> 的论据。建议报告：**在未做质量门禁时，低质量段贡献了多少比例的虚假低风险判定**。

#### 6.2.4 与硬件方案的关系

指腹实测结论是：**信号不合格不是算法问题**。质量门禁只治"运动"这类可检测伪迹，
对"灌注弱 + 基线漂移"无效。因此 v2 的正确用法是：

1. 终端侧用 `contact_check.py` / `pipeline_check.py` **先确认信号达标**，再谈 HRV；
2. 佩戴侧改善条件：手肘支撑 / 指腹轻搭（不压）/ 完全覆盖窗口 / 遮光；
3. 腕上方案需换 AFE（MAX86176 / GH3220 等）+ IMU —— 见 §10。

### 6.3 三层情绪识别引擎（`algorithms/emotion_recognizer.py`）✅

**5 类情绪**：平静 / 低焦虑 / 高焦虑 / 愉悦 / 疲劳。

```
HRV 特征 ──▶ Layer1 规则状态机（加权区间打分，conf ≥ 0.7 直接输出）
                │ conf < 0.7
                ▼
             Layer2 模糊推理（梯形隶属度 + 概率归一，conf ≥ 0.6 输出）
                │ conf < 0.6
                ▼
             Layer3 ML 分类器（随机森林，中文标签自描述）
                │ 模型不可用
                ▼
             回退 Layer1
```

- **Layer 1**：5 情绪 × 5 特征（HR / SDNN / RMSSD / LF-HF / 呼吸率）区间打分，SDNN 权重最高。计算开销 O(1)，可移植 ESP32 边缘。
- **Layer 2**：过渡区半宽 = 区间宽度的 30%，输出平滑概率分布，解决"情绪边界模糊"。
- **Layer 3**：加载 `models/emotion_model_rf.joblib`。新 bundle 自带 `classes_zh` 中文标签自描述；
  MAD 7 类映射为：Neutral→平静、Happy→愉悦、Anxiety/Fearful/Angry→高焦虑、Sad/Disgust→低焦虑。
- **风险评分**（0~100）：情绪基础分（平静 10 / 愉悦 15 / 疲劳 40 / 低焦虑 70 / 高焦虑 90）
  × 心率偏离 × SDNN 降低 × LF/HF 升高 × 置信度修正。

#### ⚠️ 6.3.1 v1 遗留缺陷：特征键名不匹配（已修复）

这是一个典型的"不报错、只静默出错"的缺陷，记录在此以警示后续维护：

> `EMOTION_RULES` 用 `sdnn_ms` / `rmssd_ms` 作判据键，而提取器输出的是 `sdnn` / `rmssd`。
> 规则层用 `if k in feats` 做守卫 → **2 个关键特征被静默跳过**，于是
> 「平静」与「疲劳」永远同分（都只剩 HR 一项），ML 层有 3 维**恒为 0**。

**修复方式**：在 `hrv_extractor.py` 中**纯增量**补别名（保留原键，不删不改），
并同步修正 `system.py`、`simulator.py` 的单位错误与 `clean_ibi`。
共 67 项测试通过，原文件备份于 `_agent_patch_backup/`。

> ⚠️ **重要提醒**：**重新下载上游源码会丢失这些补丁**。若今后要更新 Agent 本体，
> 必须先对比 `_agent_patch_backup/`。

#### ❌ 6.3.2 单模态 PPG 的天花板（必须写进论文）

**结论：单靠 MAX30102 无法达成"情绪识别 > 85%"，这不是算法问题。**

| 论证 | 内容 |
|------|------|
| **维度论证** | 情绪是二维结构（**唤醒 × 效价**），而 PPG/HRV 只提供**唤醒**这一根轴，对**效价不敏感** |
| **不可分性** | 焦虑 / 愤怒 / 恐惧（同为"高唤醒 + 负效价"）的 HRV 特征几乎相同 → **原理上不可分** |
| **上限估计** | 单模态唤醒二分类约 70~80%；文献中单模态 2~4 类分类 60~75% |
| **旁证** | 本项目同源工具包 `mad_toolkit` 在多模态 MAD 数据集上的 CV 仅 **67.1%** |

**达标路径**：加入 GSR（唤醒金指标）+ 呼吸 + IMU → 四模态可支撑 4~7 类、80~90%。

> 📌 **论文怎么写**：建议把这一节写成"模态天花板分析"，用维度论证说明为什么必须做四模态。
> 这比"我们换了更好的模型"更有说服力，也是本项目硬件方案迭代的理论依据。

### 6.4 PAD 三维回归（`algorithms/pad_model.py`，文献2）✅

#### 6.4.1 为什么需要 PAD

离散的"高焦虑"无法区分程度差异 —— "有点紧张"和"快撑不住了"得到同一个标签，
小暖的回应也就无法分级。PAD（愉悦 Pleasure / 唤醒 Arousal / 支配 Dominance）
提供**连续三维**，补上这个粒度损失。

#### 6.4.2 12 项量表与式(1) ✅

文献2 式(1) 的计分公式：

```
ValueP = (V1 − V4 + V7 − V10) / 4
ValueA = (−V2 + V5 − V8 + V11) / 4
ValueD = (V3 − V6 + V9 − V12) / 4
```

`PAD_SCALE_ITEMS` 中 **12 项按 P/A/D 交错排列**（P 在 V1/V4/V7/V10，A 在 V2/V5/V8/V11，
D 在 V3/V6/V9/V12），其中 **V2/V4/V6/V8/V9/V12 为反向题**
（防止被试的固定反应偏差，心理测量学的标准做法）。

> ⚠️ **实现细节（易错）**：为了让"填表 12 个分值 → 公式 → PAD"全程自洽，
> 表中的**左右端顺序已按式(1) 的系数符号对齐** —— 每项右端（+4）所指的属性，
> 恰好是该项系数所"奖励"的方向。测试 `test_reverse_items_actually_reverse`
> 专门锁死这一点：若有人"顺手"把某行左右对调，测试会失败。

#### 6.4.3 RulePAD（规则兜底）✅

未训练模型时使用，**零依赖、永远可用**。输入的是**相对特征值**（见 §6.6），
按生理方向性给出 P/A/D 估计与置信度。

#### 6.4.4 PCA-SVR 与评估口径 ⚠️

文献2 的做法：19 维 HRV 特征 → PCA 降维 → SVR 回归三维。

**v2 修正的一处口径问题**（重要）：

> `PADRegressor.fit()` 的 docstring 声称使用交叉验证，但 v1 实现实际是**样本内**评估，
> 导致 `metadata.ccc` 虚高到 **0.98**。
> 而 SVR 在小样本下能"记住"训练点，样本内指标**没有任何参考价值**。

修复：新增 `_cross_val()` 做 K 折 **OOF（out-of-fold）** 预测，
`metadata.ccc` 改为由 CV 写入，并加 `ccc_source` 字段标明口径来源。

**评估指标**（`_regression_metrics`）：MSE / 相关系数 ρ / **一致性相关系数 CCC（ρc）**。
CCC 比普通相关系数更严格 —— 它同时惩罚**尺度偏差**与**偏移偏差**
（测试 `TestRegressionMetrics` 验证了这种惩罚性质）。

#### ⚠️ 6.4.5 文献2 自证：PCA 在小样本下反而变差

文献2 自己的结果中，PCA 降维**没有**带来提升。这说明：

- PCA 需要足够样本才能估计出稳定的主成分方向；
- 小样本下 PCA 会丢掉判别信息。

因此本项目的 `fit()` 保留 `use_pca` 开关，默认**不强制**使用 PCA，
由 CV 结果决定。

#### ❌ 6.4.6 D 轴的低置信（必须声明）

文献2 报告的 CV 结果是 **P ρc = 0.78 / A ρc = 0.46 / D ρc = 0.30**。
**D 轴（支配度）几乎不可用。**

本项目因此：
- 在 `PADResult` 中对 D 轴标为**低置信**并强制警告；
- Prompt 注入时**只注入 P 与 A**（`build_emotion_context` 中只取 `pad['P']` 与 `pad['A']`），
  D 轴不进对话上下文；
- 文档中明确"不可单独使用 D 轴"。

> 📌 **论文怎么写**：不要笼统写"实现了 PAD 三维预测"。
> 应写"实现了 PAD 三维预测，其中 P/A 两轴在交叉验证下达到 ρc=X/Y，
> D 轴因文献报道的固有难度（文献2 仅 0.30）标记为低置信、不参与下游决策"。

### 6.5 情感动力学（`algorithms/emotion_dynamics.py`，文献3）✅

#### 6.5.1 方法来源

文献3《基于 PWE 模型的实时情绪识别与情感对话系统》给出**情绪动力学**方程组
（式 11–20），核心思想：情绪不是瞬时标签，而是**有强度、有持续时长、会衰减、
会累积成心境**的动态量。

**Plutchik 情绪轮 9 类**（8 种基础情感 + 本项目补充的 Boring）：
`joy / trust / anticipation / surprise / sadness / disgust / fear / anger / boring`

中文名见 `WHEEL_ZH`（喜悦 / 信任 / 期待 / 惊讶 / 悲伤 / 厌恶 / 恐惧 / 愤怒 / 乏味）。
效价分类 `POSITIVE_EMOTIONS = {joy, trust, anticipation}`，
`NEGATIVE_EMOTIONS = {sadness, disgust, fear, anger, boring}`。

#### 6.5.2 实现的动力学要素

| 要素 | 公式来源 | 项目行为 |
|------|---------|---------|
| 刺激响应 | 式(11) | 外部情绪概率 → 情绪强度增量（受 `interaction` 放大） |
| 有效刺激 | 式(12)(13) | 强度超过阈值才形成"有效刺激"，否则视为噪声 |
| 持续时长 | 式(12)(13) | **积极情感持续 8s / 延长因子 1.5；其他情感 5s / 1.1**（文献3 原文取值） |
| 指数衰减 | 式(17) | 无刺激时强度按 `alpha` 衰减 |
| 心境累积 | 式(20) | 情绪强度累积为 mood；**消极心境带 +0.05 回归中性偏置**（文献3 的安全性设计） |

#### 6.5.3 四档人格：已接入 vs 未接入 ⚠️（**这一节务必看**）

文献3 表 2 给出四种人格参数。`PERSONALITY_PROFILES` 原样收录：

| 档位 | `alpha` | `interaction` | `threshold` | 中文 |
|------|---------|--------------|-------------|------|
| `ideal` | 0.05 | 1.0 | 0.45 | 理想型（默认） |
| `indifferent` | 0.15 | 1.0 | 0.65 | 冷漠型 |
| `sensitive` | 0.05 | 2.0 | 0.45 | 敏感型 |
| `persistent` | 0.02 | 1.0 | 0.45 | 执着型 |

**但是** —— v2 明确区分了两类参数：

```python
# 已接入：改动会真实改变输出
WIRED_PROFILE_PARAMS = ("alpha", "interaction")

# 保留但尚未接入：改动不会改变任何输出
RESERVED_PROFILE_PARAMS = ("beta", "tm", "threshold", "fusion")
```

原因：文献3 表 2 给出六个字段 `(α, β, tm, s, C-c, fusion)`，但论文
**未给出 `β` / `tm` / `fusion` 在式(11)–(20) 中的确切位置**（它们属于原文
"情感融合"环节，本次精读未能定位到对应公式）。为避免**凭空实现**一个
貌似能调、实则语义无据的参数，这里选择如实标注为未接入，而不是自己编一个公式。

**直接后果（写进说明书与论文，不要漏）**：

1. 四档人格**确实**有行为差异（ideal α=0.05/C-c=1.0；indifferent α=0.15；
   sensitive C-c=2.0；persistent α=0.02），所以"切换人格会改变响应"这句话成立；
2. 但「冷漠型」的**高阈值语义没有生效** —— 它当前只表现为"衰减更快"，
   而不表现为"需要更强的刺激才能被激起"。同理「敏感型」的 n-linear 融合、
   「执着型」的自适应融合都未实现；
3. 因此对外描述这四档时，只能说**"调节情感衰减速度与刺激放大倍数"**，
   **不可**说"调节情感阈值"。

这条边界由契约测试锁死：`test_reserved_params_really_have_no_effect`
会验证"改动未接线参数不影响输出"。日后若真接入，该测试失败 → 应当更新的是**文档**，
而不是改掉断言。

#### 6.5.4 `EXTINCT_TOL`：一个数学上的不动点陷阱 ✅

这是一个**只有把数学推到底才会发现**的缺陷，记录如下：

> 式(17) 中 `hi1` 是一个**吸引不动点** —— 当强度恰好等于 `hi1` 时，衰减方程的
> 增量为零。也就是说 `E ≤ hi1` 在数学上**不可达**（只会无限逼近）。
> v1 用 `if E <= hi1: 归零` 判断熄灭，导致 **durations 永远不归零**，
> 情绪状态层长期上报"unaware 级别的非零情绪"。

修复：引入

```python
EXTINCT_TOL = 1e-3   # 相对容差：强度距 hi1 不足 0.1% 即认定已熄灭
extinct_at = hi1 * (1.0 + EXTINCT_TOL)
```

该容差**只影响"何时归零"，不影响任何衰减轨迹**。
测试 `test_extinct_tolerance_is_required` 锁死这一行为。

### 6.6 相对个体基线（文献1「相对特征值法」）✅

#### 6.6.1 方法

文献1 应对个体差异的核心手段：**先测个人平静基线，再把所有特征转成相对基线的变化率**。

```
相对值 = (基线值 − 当前值) / 基线值
```

**符号约定**：**正值 = 当前值低于基线**。例如"高焦虑"时 RMSSD 下降 → 相对值为正。

`RELATIVE_KEYS` 共 14 个：`hr_bpm` / `sdnn_ms` / `rmssd_ms` / `pnn50_pct` / `lf_hf` /
`sdsd_ms` / `sd1_ms` / `sd2_ms` / `sd_hr_bpm` / `sdnn_index_ms` / `sampen` /
`dfa_alpha1` / `total_power_ms2` / `lf_nu`，钳位 ±3.0。

#### 6.6.2 实证支撑 ✅

本项目仿真链路（`esp32_firmware/bridge.py --calib`）实测：
**个人基线归一化把准确率从 85.4% 提升到 96.6%**，具体修复了「愉悦」类
从 27% → 83% 的问题。与文献1 结论互证。

> ⚠️ **这个 96.6% 不能作为最终结论**：它是**同源自洽验收**（用同一套模型生成数据、
> 再用同一套规则评判），**不是人体实验**。真值必须来自 20 人实验的 `self_report`。
> 详见 §13。

#### 6.6.3 v1 的一处量纲陷阱（已修复）✅

这是本轮的**重要缺陷之一**，值得单独说明：

> v1 的 `relative_features()` 以 `out = dict(feats)` 起手，声称是"相对值"，
> 但实际上把**没有基线、只能保留原值**的特征一并返回。
> 而基线通常只有 **7 个键**，`RELATIVE_KEYS` 却有 **14 个** —— 于是
> `sampen = 1.5`、`dfa_alpha1 = 1.02` 这类**原始量纲值**被消费方当成
> "相对基线偏移 +1.5"来读。
>
> 后果不是报错而是**静默错误**：`pad_tool._explain` 把"样本熵 1.5"
> 解读为"显著低于平时基线"，并因为它数值最大而**挤掉真正有意义的偏移**，
> 排在归因列表第一位。
>
> 混在同一套键空间里的两种量纲**没有任何标记可以区分**，所以正确做法是
> **不放进来**，而不是"保持原值"。

**修复契约**：`relative_features()` 现在**只返回真正完成相对化的特征**，
值域 ±clip；缺基线、缺当前值、基线过小的特征**不出现在结果中**。
docstring 加了 `.. warning::` 明示"结果里绝不含原始量纲的值"。
测试 `test_all_returned_values_are_ratios_not_raw` 锁死。

### 6.7 主动触发决策（`algorithms/trigger_engine.py`）✅

#### 6.7.1 风险合成

```
综合风险 R = 当前情绪风险
           + 恶化趋势加成（≤ TRIGGER_TREND_MAX）
           + 持续时长加成（≤ TRIGGER_DURATION_MAX）
           + 个体基线偏离加成
           + 心境底色加成（权重 TRIGGER_MOOD_WEIGHT = 12.0，v2 新增）
           + 情感强度加成（权重 TRIGGER_INTENSITY_WEIGHT = 15.0，v2 新增）
           → 截断 [0, 100]
```

v2 相比 v1 新增了两项：**心境底色**（坏心情让烦躁更"黏"）与
**情感强度**（同样"高焦虑"，强度 0.3 与 0.9 不应同等对待）。

#### 6.7.2 触发等级

| R 区间 | 等级 | 策略 | 说明 |
|--------|------|------|------|
| < 60 | `none` | — | 长时间无交互（默认 2h）触发「陪伴式低频问候」 |
| 60–80 | `low` | 轻微问候 | "感觉你今天有点累呢，还好吗？" |
| 80–90 | `medium` | 主动对话 | 先共情再邀请倾诉 |
| 90–99 | `high` | 呼吸练习指导 | 安抚 + 节奏呼吸引导 |
| ≥ 99 | `emergency` | 危机干预协议 | 热线转介（仅极端情形） |

#### 6.7.3 两道新增门禁（v2 核心）✅

**门禁一：信号质量**

```python
if config.QUALITY_GATE_ENABLED and quality:
    q_ok = bool(quality.get("quality_ok", True))
    if not q_ok:
        return TriggerDecision(should_trigger=False,
            reason=f"信号质量不达标（{quality.get('quality_level','?')}，"
                   f"抖动指数 {quality.get('jitter',0):.3f}）→ 暂不触发",
            metadata={"raw_risk": current_risk, "gate": "quality", "quality": quality})
```

**设计意图**：宁可这次不打扰，也**不基于假信号去关心用户**。
低质量数据下的"关心"是噪音驱动的，会显著损害用户对系统的信任。

**门禁二：连续确认**

```python
need = max(1, int(config.TRIGGER_MIN_CONSECUTIVE))   # 默认 1
if r >= low_t and self._consecutive_pass < need:
    return TriggerDecision(should_trigger=False,
        reason=f"待确认（连续 {self._consecutive_pass}/{need} 次越过阈值）",
        metadata={"raw_risk": current_risk, "gate": "consecutive"})
```

**设计意图**：情绪的生理指标存在正常波动，单点越阈值可能是伪迹残留。
设 `TRIGGER_MIN_CONSECUTIVE=3` 可显著降低误报，代价是响应延迟约 2 秒。

> **emergency 例外条款**：`emergency` 级**不受质量门禁与连续确认限制**。
> 这是经过权衡的 —— 漏掉一次真实危机的代价远大于一次误报。
> 该例外由测试 `test_emergency_bypasses_gates` 明确锁死。

#### 6.7.4 冷却与自适应阈值

- **冷却机制**：两次触发最小间隔 `TRIGGER_COOLDOWN_SEC = 300`（秒），避免打扰；
  `emergency` 不受冷却限制。
- **个体基线**：与用户平静期基线（EMA 更新，`BASELINE_ADAPT_RATE = 0.05`）
  的心率偏差 >15% 时风险上调；基线采集要求 `BASELINE_MIN_QUALITY = 0.5`
  （**低质量数据不进基线**，否则基线本身被污染）。
- **反馈自适应**：干预有效 → 阈值 **+1.5**（减少打扰）；无效 → **−1.0**（更早介入）。
  策略有效率用于下次策略选择。**v2 升级为双粒度**：既统计策略级有效率，
  也统计**技能级**有效率（22 项技能各自的有效率驱动 `match_skills` 排序）。
- 所有决策输出 `reason` 与 `metadata`（含 `gate` 字段表明被哪道门禁拦下），
  **可解释、可复盘**。

### 7.1 陪伴 Agent「小暖」（`agent/companion_agent.py`）✅

继承架构对齐 HelloAgents 教程章节 7 `MySimpleAgent`（框架可用时直接继承 `SimpleAgent`，
不可用时内置兼容实现，外部接口一致）。

**核心接口**：

| 方法 | 作用 |
|------|------|
| `run_with_emotion(message, state)` | 带 `[系统感知]` 上下文的对话 |
| `proactive_trigger(state, decision)` | 主动发起关怀（非被动等待） |
| `run(message)` / `stream_run(message)` | 标准对话 / 流式对话（含工具调用循环） |
| `run_tool(name, params)` | **v2 公开入口** —— 供路由层调用工具（见下） |
| `run_self_report(params)` | 主观自评快捷入口 |

**v2 新增 `run_tool()` 的理由**：

v1 中工具引用保存在私有属性 `_tool_refs` 里，路由层为了调用工具不得不访问私有成员。
v2 把它提为公开方法，并加了注册表兜底：

```python
def run_tool(self, name: str, params: Optional[Dict] = None) -> str:
    tool = self._tool_refs.get(name)
    if tool is None:
        # 兜底：hello_agents 的注册表接口与内置版不完全一致
        fn = getattr(self.tool_registry, "get_tool", None)
        if callable(fn):
            try: tool = fn(name)
            except Exception: tool = None
    if tool is None:
        raise KeyError(f"未装配工具 '{name}'，可用: {sorted(self._tool_refs)}")
    return tool.run(dict(params or {}))
```

工具注册名（共 9 个）：`emotion_tool` / `pad_tool` / `comfort_tool` / `breathing_guide` /
`self_report_tool` / `memory_tool` / `recall_tool` / `crisis_tool` / `referral_tool`。

#### 7.1.1 情绪上下文注入（v2 大改）✅

**注入格式**（`agent/prompts.py::build_emotion_context`）：

```

情绪状态: 高焦虑
情感动力学: 强度偏高、已持续约 40 秒、心境略偏负
维度倾向: 愉悦度 −2.3、唤醒度 +1.8（−4~+4，正=更愉悦/更兴奋）
紧张程度: 偏高（有些紧绷）
信号质量: 良好（生理判断可用）
[用户消息] ...
```

**v2 的三个关键变更**：

1. **默认不再注入原始生理数值**，改注入语义化描述（"紧张程度偏高"而非"96 bpm"）。
   依据两方面经验：(a) 实测发现模型拿到数字后**会在回复里复述**，破坏"不直接说指标"的设定；
   (b) 数字对生成质量的边际贡献很低，而语义标签模型处理得更好。
   需要看原始值时设 `config.EXPOSE_RAW_METRICS=1`。
2. **新增 PAD 维度、情感动力学、信号质量** —— 让"有点焦虑"和"极度焦虑"得到不同回应。
   注意 PAD **只注入 P 与 A**（D 轴低置信，见 §6.4.6），
   且只在 `pad.confidence >= PAD_MIN_CONFIDENCE (0.35)` 时才注入。
3. **无可用读数时直接返回原消息**（见 §7.1.2）。

#### 7.1.2 `is_usable_state()`：把"不知道"和"很放松"区分开 ✅

这是 v2 修复的一个**语义性缺陷**：

> v1 对"数据积累中"的状态会渲染出「紧张程度: 低（很放松）」——
> 也就是**把"不知道"说成了"很放松"**。这不是显示 bug，是**主动误导**。

修复：抽出唯一判据，`build_emotion_context` 开头提前返回，`CompanionAgent._has_meaningful_state`
委托同一个函数（判据唯一化，避免两处判断不一致）：

```python
_NOT_A_READING = ("数据积累中", "未识别", "N/A", "unknown", None, "")

def is_usable_state(state) -> bool:
    if not state:
        return False
    if state.get("emotion") in _NOT_A_READING:
        return False
    return state.get("layer") not in ("insufficient_data",)
```

测试 `test_accumulating_state_is_plain` 与
`test_is_usable_same_as_agent_helper`（同源验证）锁死。

#### 7.1.3 质量不佳时的显著提示 ✅

低质量信号时，Prompt 中会注入一段**加粗提醒**：

```
【重要】当前生理信号质量不佳（可能手没放稳或只是轻微活动），
上面的情绪判断仅供参考。请**以用户自述为准**，
不要根据生理数据下任何断言，也不要主动提及你检测到了什么。
```

最后一句很重要：**不要让用户觉得"你在监控我"**。

#### 7.1.4 系统提示词中的字段定义 ✅

v1 的系统提示词**从未定义过那 5 个情绪标签** —— 模型只看到 `情绪状态: 低焦虑`，
却不知道"低焦虑"相对"高焦虑"是什么位置。v2 补了「你会收到的 [系统感知] 字段含义」小节，
明确：
- 5 类情绪各自的含义与建议语气；
- 「紧张程度」是 0–100 的综合风险分，按区间映射为语义标签；
- 「情感动力学」的强度/持续/心境三项读法；
- 「信号质量」的含义，以及不佳时**以用户自述为准**。

### 7.3 长期记忆：FTA 情境单元（`agent/memory_manager.py`）✅

#### 7.3.1 从 v1 的三记忆到 v2 的 FTA 五元组

v1 实现三种记忆：**语义记忆**（用户画像 + 生理基线）、**情景记忆**（互动记录）、

v2 依据文献5（FTA-Mem）引入**情境级**结构。文献5 的核心发现：

> **情境级 > 会话级 > 轮对级** —— 以"一件事"为单位组织记忆，

| 元素 | 内容 | 例 |
|------|------|-----|
| `x_F` 事实锚 | 发生了什么 | "下周五有高数补考，还没复习" |
| `x_T` 时间锚 | 何时（绝对 + 相对） | "下周五"、`created_ts` |
| `x_A` 情感锚 | 当时的情绪 + **置信度** | 高焦虑 / conf 0.82 |
| `e` 证据指针 | 指向原始互动/时间线记录 | `interaction_id` |

共 8 张表 + 8 个索引。

#### 7.3.2 混合检索 ✅

```
R = λ · s_emb + (1 − λ) · c_struct
λ = 0.8（MEMORY_RETRIEVAL_LAMBDA）
τ = 0.35（MEMORY_RETRIEVAL_TAU，低于此分不召回）
K = 6（MEMORY_FTA_TOP_K）
```

`s_emb` 是语义相似度，`c_struct` 是**结构化匹配度**（时间邻近 + 情感一致 + 实体重合）。
文献5 的消融实验显示**去掉时间退化最严重**，因此时间锚在 `c_struct` 中权重不低。

#### 7.3.3 时序链接 ✅

`memory_links` 表支持三种关系：
- `updates` —— 后一条更新了前一条（"考试时间改了"）
- `contradicts` —— 相互矛盾（需提示用户澄清）
- `followup_of` —— 后续进展

**为什么需要**：单条记忆无法表达"这件事的演变"，而用户真正关心的是**事情怎么发展的**。

#### 7.3.4 遗忘曲线（文献4 MemoryBank）✅

```
保留度 R = e^(−t / S)          # S 为记忆强度
召回一次：S += MEMORY_STRENGTH_GAIN (1.0)，并重置 t
低于 MEMORY_RETENTION_FLOOR (0.15) → 归档
```

⚠️ **归档不等于删除** —— 归档只是从默认检索池移出，数据仍在库中，
便于调试与合规（用户行使"被遗忘权"时是显式删除，见 §7.3.6）。

#### 7.3.5 ⚠️ 能力边界：partial 融合只在词面连续时触发

**这是必须写进论文的一条限制。**

FTA 的 `partial` 机制设计意图是：一件事先说了一半，后面又提到，
应当**跨段携带并融合**成完整单元。

但本系统在**无嵌入模型**时，相似度用**字符 bigram 重叠系数**
（Szymkiewicz–Simpson 系数，替代 Jaccard 以避免短串被过度惩罚）作代理。
它的致命弱点是：

> **词面不重合即得 0 分**。例如
> `_similar("我最近在准备一个考试", "就是下周五的高数补考，还没复习") = 0.0`

这两句在语义上明显是同一件事，但字符 bigram 完全不重合 → **不融合、不互相召回**。

**因此不能宣称"能自动把同一件事的两次提及连起来"。**

正确表述是：**"在两次提及存在词面连续时，系统能把它们融合成一个完整情境单元"**。

这条限制被**故意写成测试契约**（`test_fusion_requires_lexical_continuity`），
防止文档/汇报出现不成立的宣称。日后接上真向量后端使该测试失败时，
**应当更新的是文档，而不是改掉断言**。

#### 7.3.6 数据权利（文献5 伦理要求）✅

文献5 要求系统支持**知情同意 / 数据权利 / 查看·更正·删除·留存控制**。落地为：

| 方法 | 功能 |
|------|------|
| `export_user_data()` | 导出全部用户数据（JSON），支持**可携带权** |
| `purge_user_data(keep_profile)` | 清除数据，可选择保留画像 |

| `update_user_profile(updates)` | 更正画像 |

对应端点：`GET /memory/export` / `POST /memory/purge`。
`config.PRIVACY_NOTICE_VERSION = "v1.1"` 标识隐私声明版本 —— 声明更新时需要重新取得同意。

#### 7.3.7 一处真实缺陷：融合时漏补置信度

> FTA partial 融合时只补了 `emotion` 字段，**没补 `emotion_conf`**。
> 后果：刚被用户亲口确认的情感锚，带着 **0.0 的置信度**，
> 被 `recall_tool` 标成"仅供参考" —— 也就是**用户自己说的话反而比算法猜的更不可信**。

修复：融合 SQL 中同步更新置信度：

```sql
emotion=COALESCE(NULLIF(?,''), emotion),
emotion_conf=CASE WHEN NULLIF(?,'') IS NULL THEN emotion_conf ELSE ? END,
physio_json=COALESCE(NULLIF(?,''), physio_json)
```

### 7.4 主观-客观校准：让「>85%」有真值 ✅（v2 核心新增）

#### 7.4.1 问题

大创核心指标之一是「**情绪识别准确率 > 85%**」。但**生理信号本身没有真值** ——
没有一种传感器能直接读出"这个人现在是什么情绪"。
若无真值，>85% 这个数字**无法验证**，也就无法写进结题材料。

#### 7.4.2 方案

系统内置**主观自评通道**（1~10 分），`self_report` 表把
**用户自评与客观侧快照成对落库**：

```
self_report(score, emotion, note, ts,
            -- 客观侧同一时刻的快照 --
            predicted_emotion, predicted_risk, quality_level, ...)
```

三个用途：

1. **主客观不一致时，以用户为准** —— 伦理要求：**用户对自己的状态有最终解释权**；
2. **累积个人标注数据**，为 20 人实验提供真值来源；
3. **校准个体基线** —— 缓解"腕/指式 PPG 灌注差异导致阈值漂移"。

#### 7.4.3 冲突处理

```python
SELF_REPORT_CONFLICT_GAP = 3.0        # 主观与客观差异超过 3 分 → 判为不一致
SELF_REPORT_CONFLICT_DISCOUNT = 0.5   # 不一致时，生理侧置信度乘 0.5
```

`GET /self-report/consistency` 返回一致性统计（一致率、偏差分布），
可直接作为论文中的"主客观一致性分析"。

> 📌 **论文怎么写**：>85% 这一指标的**正确口径**是
> "在 `self_report` 真值下的分类准确率"，且必须写明样本量与采集方式。
> 目前系统**只完成了采集与配对机制**，尚未有人体数据 —— 这是 ✅ 实现 + ❌ 未验证，
> 两者都要说清楚。

## 八、核心编排层（闭环数据流）

`core/system.py` 的 `HeartCompanionSystem` 是闭环中枢，1 秒主循环：

```
ingest_sensor(packet)
  ├─ ① IBI 窗口累积（HRV_WINDOW_SEC=300）+ 特征提取 extract_from_ble()
  ├─ ② 信号质量评估 quality_metrics()          ★ v2
  ├─ ③ 三层情绪识别 → 状态快照
  ├─ ④ PAD 三维估计（RulePAD 或 PCA-SVR）      ★ v2
  ├─ ⑤ 情感动力学推进 update_from_zh()          ★ v2
  ├─ ⑥ 记忆沉淀（时间线 + 基线 EMA + FTA 情境单元）★ v2
  └─ ⑦ 返回 state

check_trigger()
  ├─ 风险合成 R（含心境底色 + 情感强度）
  ├─ 门禁一：信号质量                           ★ v2
  ├─ 门禁二：连续确认                           ★ v2
  ├─ 冷却判据（emergency 豁免）
  └─ 若触发 → 策略选择 → 小暖主动关怀 →（TTS）

chat(message)
  ├─ 情绪上下文注入（语义化 + 质量提示 + 动力学）
  ├─ FTA 记忆检索与注入
  ├─ LLM 生成（含工具循环）
  ├─ FTA 情境单元捕获 _capture_fta()
  └─ 存互动

feedback(effective)
  └─ 干预前后风险对比 → 策略级 + 技能级有效率 → 个体阈值更新
```

**数据保护**：心跳样本 < 5 拍且无固件特征时输出「数据积累中」，
避免小样本误判（并由 `is_usable_state()` 保证不会渲染成"很放松"）。

**手动情绪注入**（`set_manual_emotion`）：硬件未接入时可用 CLI `/心情 高焦虑`
或 API `POST /emotion/manual` 注入模拟状态，小暖会按该状态调整语气。
用于验证情绪自适应对话与前端联调。

**传感器模拟器**（`core/simulator.py`）：按情绪剧本生成 IBI 随机游走 + 运动伪迹，
特征由提取器**真实计算**（非直接伪造），输出与四模态契约包格式一致。
内置 4 个场景：`stress_event` / `anxiety_attack` / `afternoon_fatigue` / `happy_chat`。

### 9.3 视图换算层（`backend/views.py`）✅

v2 抽出的一层**纯函数**，不依赖 FastAPI。职责：把内部状态换算成对外视图。

**PAD → 程度映射**（工程取值，docstring 已声明）：

```python
_DETAIL_WEIGHTS = {
    "anxiety_level": (-1.20, 1.00, 0.00),   # 效价↓ 唤醒↑
    "stress_level":  (-1.00, 1.00, -0.40),  # 效价↓ 唤醒↑ 支配↓
    "fatigue_level": (-0.80, -1.00, -0.60), # 效价↓ 唤醒↓ 支配↓
}
def score(key):
    wp, wa, wd = _DETAIL_WEIGHTS[key]
    return _CENTER + _SCALE * (wp * p + wa * a + wd * d)   # _CENTER=50, _SCALE=25
```

其他职责：`clamp()` / `band(score)`（语义区间）/ `detail_from_pad()` / `detail_from_table()`
（查表兜底）/ `detail_view(state)` / `public_state(state)`（裁剪原始值）。

**为什么值得单独成层**：26 项测试无需 Web 框架即可运行，
且"PAD 值怎么变成紧张程度"这类最易出错的逻辑有了覆盖
（含 `test_continuous_not_stepwise` 验证**不会阶跃跳变**、
`test_both_layers_derive_from_config` 验证配置同源）。

## 十、硬件接入指南（与四模态方案同步）

> **本节与当前硬件方案完全同步**。⚠️ **早期方案中的 LD2410 雷达已退役**，
> 不再讨论其波特率与协议。

### 10.1 终端硬件（四模态）

| 器件 | I2C 地址 | 作用 | 备注 |
|------|---------|------|------|
| **MAX30102** | `0x57` | PPG 光电容积脉搏波 → 逐拍 IBI | 适合**指腹**；腕上灌注弱一个数量级 |
| **MPU6050** | `0x68` | 六轴惯性 → 运动伪迹门控 | INT → GPIO17（可选，主固件轮询） |
| **ADS1115** | `0x48` | 16bit ADC → GSR 皮电 | **A0 是唯一非总线的线**；PGA = **±4.096V**；ADDR/AD0 → GND |
| 呼吸带 | 预留 | 胸腹呼吸 → 直接呼吸率 | 与 RSA 交叉校验 |

**总线拓扑**：四者**并联 I2C**：`SDA=GPIO21` / `SCL=GPIO22`，上拉并联 ≈ 3.3kΩ，400kHz 正常。
`i2c.scan()` 期望返回 `['0x48', '0x57', '0x68']`。

**⚠️ 三条供电铁律（违反会损坏器件）**：

1. **GSR 与 ADS1115 必须同 3.3V** —— GSR 若接 5V，其输出 5V > ADS1115 的
   `VDD + 0.3 = 3.6V`（绝对最大额定值）；
2. **MAX30102 模块也必须接 3.3V** —— 接 5V 会把模块上拉灌进 GPIO；
3. **所有 GND 必须共地** —— 面包板上下轨**默认不通**，需自行跳线。

**GSR 电极佩戴**：同手**食指 + 中指指腹**，静置 2~3 分钟。
**MPU6050 必须与 PPG 同夹具**（否则测的不是同一段运动）。

### 10.2 契约数据包（1 包/秒，9 字段）

```json
{
  "t": 1700000000,
  "hr": 92,
  "ibi": [660, 655, 650],
  "sdnn": 26.0,
  "rmssd": 18.0,
  "pnn50": 4.0,
  "lf_hf": 4.0,
  "rr": 21.0,
  "sig_quality": 0.9
}
```

| 字段 | 说明 |
|------|------|
| `t` | 时间戳（秒） |
| `hr` | 心率 bpm |
| `ibi` | **最近 3 拍**的间期（ms） |
| `sdnn` / `rmssd` / `pnn50` / `lf_hf` | 固件侧已算的 HRV 特征 |
| `rr` | 呼吸率（次/分） |
| `sig_quality` | 固件侧质量分（0~1） |

> ⚠️ **`ibi` 字段的一个已知语义问题（对接时必看）**：
> 契约规定 `ibi` 是"最近 3 拍"，但设备**每秒发一包**，
> 而正常心率下每秒约产生 1.2 拍 —— 于是相邻两包的 `ibi` 会出现 **2 拍重复**。
>
> 本项目的固件 `esp32_firmware/main.py` 因此**额外输出
> `ibi_new`（本包新增的拍，无重复）**，桥接器 `bridge.py`
> 在解析时**优先取 `ibi_new`**（取不到才回退到 `ibi`）。
>
> - 若使用本项目桥接器：**优先消费 `ibi_new`**；
> - 若自己写上位机：需要自己按 `t` 与末位对齐去重，**否则会重复计入 RR 序列，
>   把 RMSSD 系统性压低**；
> - 只有在需要严格符合契约时才用原始 `ibi`（`ibi_new` 是**契约之外的诊断字段**）。

**缺字段处理**：后端**优先采用固件已算值**；缺失字段**由 IBI 重算**；
完全缺失时按心率经验式兜底。因此固件可以只上传 `ibi` 与 `hr`，
但那样后端负载会上升（推荐固件算 5 分钟窗的 SDNN/RMSSD/pNN50）。

### 10.3 运动门控（IMU）✅

`hrv.add_sample(ir, motion=bool)` —— **运动期只跑滤波器，不记录峰、不记 RR**。

> **为什么在源头做门控，而不是事后清洗**：源头闸门优于事后清洗。
> 事后清洗无法区分"真实的短 RR"与"伪迹造成的假短 RR"。

**v2 关键修复**：**运动跳变时必须清 state**（`last_peak_t=None, peaks=[]`）。
否则会用"运动前最后一个峰"与"运动后第一个峰"算出一个**跨段的假 RR**，
**直接污染 RMSSD**。

**离线验收结论**（`gate_check.py`，5 项全过）：

| 项 | 结果 |
|----|------|
| 运动段未门控 | RMSSD **虚高 1.78×**（35.2 → 62.6 ms） |
| 门控段 | **一拍不收**（完全隔离） |
| 静止段 | 1.00×（**零误伤**） |

**MPU6050 判据必须三取或**：

```python
|‖a‖ − 1g| > 0.25g  或  |ω − 零偏| > 20°/s  或  tilt > 8°
```

> ⚠️ **只用加速度模长会大面积漏检**（实测手晃板子时仅覆盖 ~16%）。
> 原因有几何必然性：**旋转不改变 |a|**，而手抖的主动成分恰恰是**转动**。
> 判据②（角速度）覆盖 98%，但**必须先扣零偏**
> （实测零偏 (+3.95, +1.59, +0.12)°/s）。

**MPU6050 的 `WHO_AM_I = 0x75` 非标准值**（等于寄存器地址，说明该 die 未实现）
⇒ **不可用它判断器件可用性**！改用**寄存器写-回读校验**
（`SMPLRT_DIV` / `CONFIG` / `ACCEL_CONFIG` / `GYRO_CONFIG` / `PWR_MGMT_1,2` → 6/6 一致即可用）；
多块时必须**逐块验证**。

### 10.4 信号质量门禁（软件侧，v2）✅

除固件侧的 `sig_quality` 外，**后端独立计算** jitter 与伪迹率
（见 §6.2）。二者**互为补充**：

- 固件侧 `sig_quality` 反映**采集当时**的接触与信噪；
- 后端 jitter 反映**逐拍序列**的可信度 —— 这是固件看不到的。

`BASELINE_MIN_QUALITY = 0.5`：低质量数据**不进基线 EMA**，否则基线本身被污染。

### 10.5 接入方式（三种）

```python
from hrv_companion_agent.core.system import HeartCompanionSystem
```

### 10.7 MAX30102 硬件级铁律（实测标定）

这些是踩过坑才得到的结论，**违反会得到"看起来正常但完全错误"的数据**：

| 铁律 | 违反后果 |
|------|---------|
| **ADC 量程必须 16384nA** | 4096nA 会把信号压紧削顶 → IR 恒 262143 → **HR 虚高 163 bpm**。<br>⚠️ **饱和 ≠ 算法问题，先查量程** |
| **LED 电流必须自适应** | 比例搜索 `code × target / dc`；改档后**等 400ms**（FIFO 深 32 残留 320ms）；<br>收敛判据须"落在 target±50% 内才 break"（target 60000）；定档后**必须复测** |
| **`num_available()` 直读硬件** `RD_PTR`/`WR_PTR` | 软件计数会错位 3 字节 → **RED/IR 读反** |
| **不应期 ≥ 450ms** | 主峰后 0.30~0.35s 有**重搏波**；用 300ms 会双计 → RR 减半 → **HR 翻倍（166bpm）** |
| **时间戳按样本序号 × 10ms 自动计时** | 给整批 FIFO 打同一个 `ticks_ms()` 会让所有 RR 塌成 0 |
| **门限不可用"快升慢降"包络** | 一次伪迹会把门限抬爆 → 真实脉搏**全漏** |
| **内存红线** | 不可缓存长波形（60s × 100Hz = 6000 点 → `MemoryError`）。用 200 点 + 512 RR |
| **OVF_COUNTER 须主动写 0** | 该兼容 die 读后**不自清** |

**信号处理链**：

```
HP EMA(α=.02) → LP EMA(α=.25) → 抛物线插值峰位
→ 门限 = peak_ratio × 近期峰幅中位数
→ 不应期 max(450ms, 0.6×中位RR) → RR 离群迭代剔除
```

**实测健康值**：IR 直流 ≈ 9.7 万 / 脉搏幅度 ≈ 1000 / HR 70~78 / 采样率 100.7~101Hz。
`gain_ok=True` 才算贴合。**IR p2p 仅几十 → 无手指**。

### 10.8 ⚠️ 【核心结论】指腹测不出可信 HRV（必须写进论文）

这是本项目**最重要的硬件侧结论**：

> 2026-09-30 指腹实测：HR 73 bpm **看着正常**，
> 但 **RMSSD 130ms / pNN50 61~75%**（静息应 20~50ms / <10%）。
> → **HR 可信，HRV 是假的**。

`contact_check.py` 三项**全不合格**：
PI 0.454%（需 ≥0.8%）/ 幅度 CV 132%（需 ≤30%）/ jitter 0.455（需 ≤0.12）。

**波形层面的证据**：

| 现象 | 数据 |
|------|------|
| 脉搏带（0.7~3Hz）功率占比 | **0.01%**（漂移带占 99.99%） |
| 相邻心搏幅度 | **差 3 倍** |
| 双峰形态 | 隔 176ms，幅度 678 vs 679（**近相等**）→ 早到的假峰把真峰顶进不应期 |
| (短, 长) RR 对 | 656 + 997 ≈ 2 × 826（**成对出现**） |

**尝试过的其他基准点**（峰位 / max-slope / 足点）：
130.5 / 174.6~236.0 / 206.0 ms —— **足点无优势**。
加 (短,长) 修复策略得 28.5，但**修复率仅 29%**，
且参数扫描时结果在 28~365ms 剧烈波动 —— 即**在拟合噪声**。

**诚实结论**：
**这不是算法问题，是指腹信号本身不合格。**
运动门控只能治"运动"这类伪迹，对"**灌注弱 + 基线漂移**"无效。

**正确应对**：
1. 必须改善采集条件（**手肘支撑 / 指腹轻搭不压 / 完全覆盖窗口 / 遮光**）；
2. 用 `contact_check.py` **确认达标后再谈 HRV**；
3. ⚠️ 腕上方案需换 AFE（MAX86176 / GH3220 等）+ IMU ——
   `MAX30102` 挪到手腕**更差**（灌注弱一个数量级，且光学设计面向指腹）。

**已排除的方案**：雷达（需 0.4~1.5m 距离）/ EmbracePlus（不能实时流）/
MAX86150（已 Obsolete）。零硬件 RSA 优先；接触式备选 HKH-11C。

### 13.3 真值采集方案（`self_report`）

```
实验流程（每名被试）：
  ① 知情同意（含隐私声明 v1.1，明确可撤回、可导出、可删除）
  ② 采集个人静息基线（≥5 分钟，质量须达"合格"）

```

**准确率计算口径**：以 `self_report` 为真值，计算 5 类分类的
准确率 / 混淆矩阵 / 各类 F1。**必须报告各类指标，不能只报总体准确率**
（类别不平衡下总体准确率会误导 —— 这正是文献1 八分类仅 13.75% 的教训）。

### 13.4 阴性对照与数据泄漏检查

**这是本项目的管线自检机制，建议写进论文的"方法可靠性"一节**：

`train_pad_model.py --synthetic` 生成的数据中，
**D 轴刻意不接任何生理特征**。因此：

```
期望：CV ρc(D) ≈ 0
实测：CV ρc(D) = −0.0775   ✅ 通过
```

若结果明显大于 0，说明 **K 折切分存在数据泄漏**（例如先归一化再切分、
或特征中混入了标签信息），必须先修管线才能相信任何指标。

同样的自检也用于情绪分类：`tests/test_pad_model.py::TestCrossValHonesty::_negative_control_no_leakage`
用**随机标签**跑 CV，断言 ρc < 0.35。

> 📌 **论文怎么写**：把"我们用阴性对照验证了评估管线无泄漏"写进方法学，
> 比单纯报一个高指标更有说服力 —— 它证明指标**不是算错的**。

### 14.3 测试方法论（v2 确立，值得沿用）

**① 对渲染结果断言，而不是对内部变量断言**

v2 修复的 Prompt 层缺陷有一个**共同特征**：

> 程序照跑、日志干净、单测全绿，**只有把实际输出打出来才看得见**。

例如 `_QUALITY_LABELS` 键名不匹配导致"信号质量"这一行**从未被注入过** ——
任何断言内部变量的测试都会通过。因此 Prompt 层测试一律断言**渲染出的字符串内容**。

**② 把能力边界写成测试契约**

对于已知不成立的能力，v2 的做法是**写一条断言它不成立的测试**，
而不是只在文档里提一句。例如：

```python
def test_fusion_requires_lexical_continuity(self):
    """词面不重合 → 不得融合（能力边界，故意写成契约）。

    防止文档/汇报出现"能自动把同一件事的两次提及连起来"的宣称。
    日后接上真向量后端使该测试失败时，应当更新文档，而不是改掉断言。
    """
```

同类的还有 `test_reserved_params_really_have_no_effect`（人格参数未接线）、
`test_relaxing_threshold_changes_verdict`（配置非装饰）。

**③ 阴性对照验证评估管线**

见 §13.4。

**④ 中文正文里写 ASCII 双引号会炸 Python 字符串定界符**

docstring 尤其容易中招（写"填了就忘"这种加引号的短语时）。
统一改用「」，且测试文件写完后必须跑一次 import。

## 十五、安全与伦理

### 15.1 非医疗声明

系统输出为**陪伴性支持**，**不构成**心理/医疗诊断；涉及躯体症状建议就医。
心理教育内容需自然带出 `config.PSYCHOEDUCATION_DISCLAIMER`：

> 以上是通用的心理学知识，用于帮助理解自己的状态，**不构成诊断**。
> 如果困扰持续或加重，请让专业人士陪你一起看。

### 15.2 危机干预分级 ✅

风险 ≥99 或文本检测到自伤/自杀信号 → 自动启动危机协议。
v2 分级为四级（**被动 / 主动 / 计划 / 准备**），每级有明确的
"第一步做什么"与"语气要求"（详见 §7.2.5）。

### 15.3 分层转介（L1~L4）✅

`config.REFERRAL_LADDER` 定义四级，每级给出：**适用判据 / 建议动作 / 如何开口的话术脚本**。

**关键设计原则**：

> ⚠️ **不对 L1 给热线**。低风险场景下抛出热线会造成**"狼来了"效应**，
> 削弱真实危机时热线的分量。分层转介的意义正在于此。

**核心产出是「如何向他人开口」的话术脚本** —— 这是多数系统最含糊的一环。
让用户"去找辅导员"很容易，告诉用户**具体怎么开口**才有用。

⚠️ `CAMPUS_RESOURCES` 是占位条目，**交付前必须替换为本校真实信息**。

### 15.4 直接询问准则 ✅

> **直接询问不会诱导自杀，这是国际共识。** 绕弯子反而让 ta 更孤立。

系统被明确要求**直接询问**意念（"你是有过想结束生命的念头吗？"），
而不是绕着问"你最近心情怎么样"。问完后**要等** —— **沉默是允许的**。

### 15.5 数据权利与隐私 ✅

| 权利 | 实现 |
|------|------|
| 知情同意 | `config.PRIVACY_NOTICE_VERSION = "v1.1"`，版本更新须重新取得同意 |
| 可携带 | `export_user_data()` / `GET /memory/export` |
| 被遗忘 | `purge_user_data()` / `POST /memory/purge` |
| 更正 | `update_fta_unit()` / `update_user_profile()` |
| 默认最小化 | 原始生理值默认**不下发**、**不进 Prompt**（`EXPOSE_RAW_METRICS=0`） |
| 存储 | 生理数据仅存**本地** SQLite；API Key 仅存 `.env`（已 gitignore） |

### 15.6 使用边界

鼓励用户与现实支持系统（家人 / 朋友 / 校心理中心）保持联系，
**AI 陪伴不替代真实人际关系**。这不仅是免责声明，
也是产品设计的取向 —— 系统的目标是**把人往外推**，而不是把人留在对话框里。

## 十七、常见问题 FAQ

**Q1：没有 API Key 能跑吗？**
能。系统自动进入离线演示模式（内置共情话术脑），闭环完整可演示、零费用。

**Q2：填了 API Key 却还是离线回复，为什么？**
最常见三个原因：
1. `.env` 没被加载 —— 程序启动时自动加载项目目录/上级目录的 `.env`（无需重启电脑，重启程序即可）；
2. **模型名与服务商不一致** —— 例如网关只支持 `deepseek-v4-flash`/`deepseek-v4-pro`，
   你却填了 `deepseek-flash`。系统会**自动纠错**，并在启动健康检查时直接显示「在线 ✓」或具体错误；
3. 网络/Key 无效 —— 健康检查会显示「在线但对话失败」及原因。

**Q3：换了通义千问 / Kimi / Ollama 怎么办？**
改 `.env` 的 `LLM_MODEL_ID` / `LLM_API_KEY` / `LLM_BASE_URL` 即可（OpenAI 兼容协议）。
Key 变量名任意（`DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 等都识别）。

**Q4：回复里出现重复文字或「🧠 正在调用模型」等调试信息？**
已修复：LLM 通道统一改用 openai SDK 直连，不再经过 hello_agents 客户端
（其内部会打印并重复输出），hello_agents 仅保留 Agent 框架身份。

**Q5：ML 模型加载失败？**
确认 `models/emotion_model_rf.joblib` 存在且已安装 `scikit-learn joblib`；
加载失败仅跳过 Layer 3，规则 + 模糊层照常工作。

**Q6：控制台中文乱码？**
使用 `python -X utf8 run_demo.py`；入口脚本已内置 UTF-8 重配置。

**Q7：如何导出情绪时间线给数据分析？**
`system.get_timeline(days=7)` 返回结构化列表，或直接查询 `data/memory.db` 的
`emotion_timeline` 表（可导出 CSV）。**含真值的实验数据**请用 `GET /memory/export`。

**Q8：触发太频繁 / 太迟钝？**
三个可调点：
1. `config.py` 的 `TRIGGER_LOW/MEDIUM/HIGH/EMERGENCY` 阈值；
2. **`TRIGGER_MIN_CONSECUTIVE`**（建议 3）—— 需连续 N 次越阈值才触发，抗单点误报；
3. 反馈闭环会**自动适应**（有效 +1.5 / 无效 −1.0）。
冷却间隔 `TRIGGER_COOLDOWN_SEC` 可调。

**Q9：没接硬件怎么体验"情绪感知"？**
CLI 输入 `/心情 高焦虑`（或 API `POST /emotion/manual`）手动注入情绪，
小暖会立即切换为安抚 + 呼吸引导模式；`/模拟 stress_event` 则可回放完整生理场景。

**Q10：为什么我心跳正常，系统却说"信号不可用"？** ★
**这正是 v2 质量门禁要解决的问题。** 心率与 HRV 的可信度是**解耦**的：
HR 只看峰间距均值（抖动被平均掉），HRV 看逐拍差分（抖动全额进入）。
所以**心率正常完全不能说明 HRV 可信**（实测 jitter 可达 0.455）。
请按 `/emotion/quality` 返回的 `reason` 处理：
- "逐拍抖动过大" → **佩戴问题**：手肘支撑、指腹轻搭不压、完全覆盖窗口、遮光；
- "伪迹比例过高" → **算法/搏动问题**：异位搏动或漏检双计，检查不应期设置。

**Q11：为什么回复里看不到具体心率数字了？** ★
这是有意设计。v2 默认**只注入语义区间**（"紧张程度偏高"），
因为实测发现模型拿到数字后会在回复里复述，破坏产品设定。
需要看原始值调试时设 `EXPOSE_RAW_METRICS=1`（**仅调试与论文绘图**）。

**Q12：切换人格档位（`/user/personality`）真的有效果吗？** ★
有效果，但**比你以为的少**。四档人格当前**只调两项**：
情感**衰减速度**（`alpha`）与**刺激放大倍数**（`interaction`）。
文献3 表 2 中的情感阈值、融合方式等字段**尚未接入**
（见 `RESERVED_PROFILE_PARAMS`）。
所以**可以说**"切换人格会改变响应"，**不可以说**"调节情感阈值"。

**Q13：记忆能自动把"同一件事"的两次提及连起来吗？** ★
**在两次提及存在词面连续时可以**；否则不行。
无嵌入模型时相似度用字符 bigram 重叠系数作代理，
`"我最近在准备一个考试"` 与 `"就是下周五的高数补考，还没复习"` 的重叠为 **0.0**
→ 不融合、不互相召回。
要覆盖这种情况需接真向量后端（`CHROMA_ENABLED=1`）。
这条限制被**故意写成测试契约**（`test_fusion_requires_lexical_continuity`）。

**Q14：PAD 的准确率是多少？** ★
**目前没有人体数据，不能给出准确率。**
文献2 报告的 CV 口径是 P ρc=0.78 / A 0.46 / **D 0.30**（D 轴基本不可用）。
本系统的 PCA-SVR 通路已实现且评估口径已修正为 CV，
但**达到与否必须等 20 人实验**。合成数据只能自检管线，**没有任何参考价值**。

| 11 | FTA partial 融合只补 `emotion` 不补 `emotion_conf` | 用户亲口确认的情感锚带着 **0.0 置信度**，被标成"仅供参考" | 融合时同步补置信度 |
| 12 | 系统提示词**从未定义**那 5 个情绪标签 | 模型看到"低焦虑"却不知其相对位置 | 补「[系统感知] 字段含义」小节 |

**另有 1 处接口级缺陷**（更严重，会直接影响识别结果）：

> `EMOTION_RULES` 用 `sdnn_ms` / `rmssd_ms` 作判据键，
> 而提取器输出 `sdnn` / `rmssd` —— 规则层用 `if k in feats` 守卫，
> 于是 **2 个关键特征被静默跳过**：
> 「平静」与「疲劳」**永远同分**，ML 层有 **3 维恒为 0**。
> 修复：纯增量补别名 + 修正 `system.py` / `simulator.py` 单位错误 + `clean_ibi`。
> **重下上游源码会丢失补丁**，备份在 `_agent_patch_backup/`。
